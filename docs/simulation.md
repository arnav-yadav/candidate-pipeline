# How the client data was simulated

**All client data in this project is simulated.** The client (a ~150-person D2C brand hiring customer-support
agents) is the constructed case from Assignment 1. No real person's data is used.

This page explains what was simulated, how, and what that means for the conclusions, so that no finding is
presented as more than it is.

## Why simulate, and the risk that creates

A real company's applicant data can't be published: it's personal data. So the five intake systems and the
recruiter's tracker are generated by [`simulator/generate_client_systems.py`](../simulator/generate_client_systems.py).

The risk of simulated data is that the analyst "discovers" problems they planted themselves. To limit that, the
generator encodes **mechanisms**, the ones described in Assignment 1, and not individual errors. The messiness in
the data comes out of those mechanisms:

| Mechanism in the generator | What it produces in the data (found by profiling, not written in by hand) |
|---|---|
| People have names drawn from a realistic, skewed distribution (many Rahul Sharmas) | Different people share a name, so name matching over-counts duplicates |
| Each channel captures different fields (WhatsApp: phone, rarely a name; email: an address, sometimes a phone) | No single identifier exists across every channel |
| Each channel formats phones and names its own way (`+91 98xxx`, `098…`, "Sharma, Rahul", "RAHUL SHARMA") | Representation variants that are safe to normalise |
| Some people use a second email address; ~3% of people share a phone with a sibling | Email-only and phone-only matching each fail in a different way |
| Referrers sometimes type their own phone number for the candidate | A phone number that belongs to many "different" candidates |
| One recruiter logs WhatsApp and email applicants by hand when time allows, reviewing newest first | Some applications never reach the tracker; the backlog grows with volume |
| The recruiter marks a row `DUP` when the *name* looks familiar | People wrongly marked duplicate and never reviewed |
| Rejected applicants are not told (silent rejection) | Most applicants hear nothing within 30 days |
| Applicants who hear nothing are more likely to apply again, often through another channel | Re-applications across channels |
| The tracker is typed by hand (mixed date formats, free-text statuses such as `NS`) | Ambiguous dates and statuses with no agreed meaning |
| Walk-in candidates are typed straight into the tracker | Tracker rows with no source record behind them |
| The job-board API paginates, fails once with HTTP 500, rate-limits once with HTTP 429, and repeats a record across pages | Retrieval must retry, de-duplicate across pages and prove completeness |

The generator uses a fixed seed (`20260901`) and nothing that depends on the machine or the clock, so the client
systems are byte-identical on every machine. A test (`tests/test_simulator.py`) regenerates them under different Python
hash seeds and checks they match the committed files.

## What the pipeline is not allowed to see

The generator also writes the true identity of every application to `simulator/_ground_truth/`. **The pipeline
never reads that folder.** It exists only to produce the one thing a real engagement would create by hand:
[`client_systems/audit/recruiter_labelled_pairs.csv`](../client_systems/audit/recruiter_labelled_pairs.csv), a
sample of 237 pairs of records that the recruiter has labelled "same person" or "different people". That sample is
how the matching rules are evaluated (see [data_model.md](data_model.md#identity-resolution)).

## What the simulation means for the conclusions

| Finding | Status | Why |
|---|---|---|
| The pipeline retrieves every source completely, flags quality issues, resolves identities and reproduces its outputs | **Demonstrated** | These are properties of the code, and they would hold on real data of the same shape |
| Name matching over-counts duplicates, and email + phone matching with a name check makes no incorrect merges on the labelled sample | **Demonstrated on this data; plausible in general** | It follows from name collisions and channel-specific identifiers, which any real Indian applicant pool will have. The exact rates are specific to the simulation |
| The duplicate-screening rate is ~10–15% a month, not 22% | **Illustrative only** | The level depends on the generator's settings. On real data it must be re-measured, which is exactly what the pipeline is built to do |
| Applicants who hear nothing re-apply far more (H2 over H1) | **Method demonstrated, finding not evidence** | The generator was *told* that silence drives re-application, so the pipeline finding it is circular. What the project shows is that the H1-vs-H2 test from Assignment 1 can be run, and how |

To regenerate the client systems:

```bash
python simulator/generate_client_systems.py
```
